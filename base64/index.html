3Putting Base64 in a URL: how + and / break it

Standard Base64 uses + and /. Both are meaningful characters in a URL, so the moment the value travels in a link or a query string, the meaning can change. This is the step almost every Base64 tool skips.

+ is read as a space in a query string

You send ?token=SGVsbG8+A==
Server decodes as SGVsbG8 A== — the + became a space
Result Base64 decodes to different bytes than you encoded; the token or payload is corrupted
Fix %2B for the plus, or switch to URL-safe Base64

/ splits a path segment

You send https://api.example.com/get/Pj4/Pyc=
Server sees two path segments — Pj4 and Pyc= — not one value
Result 404, or the wrong resource; the value never arrives intact
Fix %2F for the slash, or URL-safe Base64

Trailing = padding gets trimmed or misread

You send ?id=SGVsbG8=
What happens some systems strip trailing =, and inside a query value it also collides with the key=value separator
Fix %3D, or use unpadded URL-safe Base64 (what JWTs do)

Sending standard Base64 where the consumer expects URL-safe

Example a JWT segment, an OAuth state, or an AWS S3 presigned signature
Result + and / are not in the URL-safe alphabet, so the receiver fails or decodes to the wrong bytes
Fix produce URL-safe from the start: + → -, / → _

Double-encoding the escape

You percent-encode an already-encoded value
Result %2B → %252B — the receiver decodes it back to the literal text %2B, not a plus
Fix percent-encode exactly once, and only the characters that need it

atob() expects standard Base64, not URL-safe

In the browser atob('Pj4_Pyc-Pg') throws — - and _ are not valid to it
Fix translate back first: -→+, _→/, then re-add padding before calling atob()

When to use URL-safe Base64

Use the URL-safe alphabet (- and _, usually with padding dropped) whenever the Base64 value travels somewhere with URL or identifier rules:

· anywhere inside a URL — a path segment, a query parameter, a fragment
· JWT / JWS / JWK segments, OAuth state and PKCE code_verifier
· AWS S3 presigned URLs and other signatures that are specified as base64url
· filenames, headers, or anything that must avoid + and /

Stay on standard Base64 when the consumer expects it — MIME email attachments, PEM, most plain-text Base64 blobs, and default decoders such as atob(), Buffer.from(s,'base64'), base64.b64decode(). When in doubt, check what the receiving side specifies, and encode once with that alphabet.
