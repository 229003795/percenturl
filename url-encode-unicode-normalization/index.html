URL Encode Unicode: Same-Looking Text, Different Bytes

URL encoding does not automatically normalize Unicode. A precomposed é encodes as %C3%A9; an e followed by a combining acute accent encodes as e%CC%81. Compare the strings below before changing them. NFC can make canonically equivalent text match, but your application must choose that policy.

Use complete quoted JSON strings. Escapes make invisible code-point differences reproducible. Processing stays in this browser; this checker previews normalized alternatives and does not replace either input.


Locate the difference before normalizing it


  1. Capture each original JavaScript value with JSON.stringify(value). Keep that raw value alongside its encoded spelling.
  2. Paste both quoted strings in the comparator. Compare code points first, then the raw percent-encoded output.
  3. Inspect the NFC and NFKC previews separately. A match after NFC and a match only after NFKC describe different transformations.
  4. Decide the application rule before serializing a query value. If exact text matters, keep the original; if the producer and consumer agree on NFC, normalize the value before encoding it.
  5. Retest storage, lookup and any byte-sensitive comparisons with the original pair. A client-side preview cannot establish how a particular server treats the two requests.

Three different failure paths in this matrix


A composed character and a decomposed sequence: the accent pair has different original code points and different encoded values, even if your font draws them alike. NFC makes their values match. The Hangul pair reaches the same result through a syllable versus a Jamo sequence, so this is not limited to adding accents to Latin letters.


Compatibility folding is a wider choice: NFC leaves fullwidth A and ordinary A distinct; NFKC makes them match. The ligature and Roman-numeral pairs also match only after NFKC. That can be useful for a deliberately forgiving search field. It also removes a distinction that an exact identifier may need. Do not call NFKC a harmless URL repair.


An ordinary-looking space: the nbsp pair contains U+00A0 on one side and U+0020 on the other. Their raw encodings are a%C2%A0b and a%20b. NFC preserves the difference; NFKC collapses it. This is a different problem from choosing plus versus %20 for form serialization. Changing the serializer alone does not turn a non-breaking space into an ordinary space.


The case control stays unequal after both NFC and NFKC. Unicode normalization is not case folding. These controls keep an apparent fix from becoming a rule that promises every similar-looking input will match.


Decoding successfully does not prove equivalence


Our regression asserts that each encoded value decodes back to the exact string supplied to that encoding step. The raw pair can therefore pass a round-trip test on both sides while still producing different bytes. The normalized output round-trips to the normalized string, not necessarily to the original one. Keep those assertions separate.


Percent-encoding normalization is another layer. RFC 3986 discusses normalizing escape spellings and unreserved characters when comparing URIs; that does not grant permission to normalize every application identifier. Work on the intended component value. Applying a text cleanup to a complete URL can mix that decision with separators, path structure and query parsing.


Rerun the comparison


Download the Node regression script, eight fixture pairs and recorded output. Put them in downloads/ and place the shared comparison core in assets/ under the same parent folder. Then run:
node downloads/url-unicode-normalization-regression.cjs


The script checks expected equality in each mode and each encoded round trip; a failed assertion exits nonzero. It also checks that a lone surrogate is rejected. For that separate failure, use the URIError and lone-surrogate checker. All pairs here contain valid Unicode text; they test identity differences rather than malformed UTF-16.


Should I normalize all URLs to NFC?
No blanket rule follows from these fixtures. Agree on the normalization of the specific value with its producer and consumer, and test the relevant lookup. Do not rewrite an opaque or already issued identifier just because two previews match.


Does a URL encoder choose NFC for me?
The direct JavaScript encoding operation tested here preserves the distinction. Normalization is an explicit operation in the comparison. For normal component escaping, return to the URL encoder; for API syntax, see the JavaScript encoding guide.
