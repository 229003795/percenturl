① What decoding actually does

Three steps, none of them magic.

  1. Read each %XX group as one byte — %20 is byte 0x20, %C3 is byte 0xC3.
  2. Join the bytes back into a UTF-8 sequence — this is why %C3%A9 is a single character, é, and not two.
  3. Leave every other character alone — : / ? & = pass straight through, because they were never encoded.
EncodedByte(s)Decodes toNote
%2020spaceOne byte, one group.
%2B2B+A real plus sign that was encoded to survive.
%C3%A9C3 A9éTwo bytes, one character.
%E2%82%ACE2 82 AC€Three bytes, one character.
%2626&Encoded so it is not read as a parameter separator.

Why strings get encoded in the first place, measured locally: sending GET /hello world HTTP/1.1 over a raw socket to a local server returns 400 Bad request syntax, because the space is the delimiter between the three fields of the request line. %20 travels fine. Encoding is what lets content survive a trip the raw character cannot make.

② The one choice that changes your answer: +

Two conventions exist, they are not interchangeable, and picking the wrong one silently returns the wrong text.

  • RFC 3986 percent-decoding — only %XX means anything. + is a literal plus.
  • application/x-www-form-urlencoded — the HTML form convention, where + was borrowed to mean a space. Query-string parsers commonly copy it.

Below: the same input, a+b, handed to real decoders. Measured on Node.js 22 and Python 3.13.

DecoderInputResultReads + as space?
decodeURIComponent('a+b')a+ba+bNO
new URLSearchParams('q=a+b').get('q')a+ba bYES
urllib.parse.unquote('a+b')a+ba+bNO
urllib.parse.unquote_plus('a+b')a+ba bYES
urllib.parse.parse_qs('q=a+b')a+b{'q': ['a b']}YES

The asymmetry worth internalising: in JavaScript, encodeURIComponent('a b') produces a%20b — never a + — yet URLSearchParams.toString() in the same language produces q=a+b. And decodeURIComponent will not turn that + back into a space. Same language, two conventions, and they do not round-trip unless you pair them deliberately.

A server confirms the other half. Three raw requests sent to a local Python server over a socket:

Measured · raw request → what the server received
GET /hello%20world HTTP/1.1   ->  200 OK    path = /hello%20world
GET /hello+world   HTTP/1.1   ->  200 OK    path = /hello+world     # a literal plus, not a space
GET /hello world   HTTP/1.1   ->  400 Bad request syntax

A + in a URL path is a plus sign, full stop. Nothing converts it, and nothing errors — which is what makes it an easy bug to ship.

③ Four reasons a decoder returns the wrong thing

  1. The string was encoded twice. %20 encoded again becomes %2520, because the second pass encodes the % into %25. Decoding once returns the text %20, not a space. Measured in both runtimes: decodeURIComponent('a%2520b') → a%20b, and unquote('a%2520b') → a%20b. Seeing %25 inside a URL is the signature of a double encode — decode twice, or better, fix the code that encoded twice.
  2. The wrong + convention. Covered above: c++ in a query value becomes c   under the form convention. That is why an encoder writes a genuine plus as %2B.
  3. A stray or truncated %. Measured: decodeURIComponent('%') and decodeURIComponent('%2') both throw URI malformed. A percent sign left over from string concatenation does not degrade gracefully — it throws. If your decoder is failing on user input, look for a bare %.
  4. Hex case is not the problem — but it looks like one. Measured: decodeURIComponent('%3a') and decodeURIComponent('%3A') both return :. Lowercase and uppercase hex decode identically, so %3a is never the reason a decode failed.

④ Doing it in your own code

Both snippets below were run locally; the outputs shown are the actual results.

JavaScript
decodeURIComponent('caf%C3%A9%20%26%20tea')          // 'café & tea'
decodeURIComponent('q=caf%C3%A9+tea')                // 'q=café+tea'   + is kept

// for a query string, use the parser instead:
new URLSearchParams('q=caf%C3%A9+tea').get('q')      // 'café tea'

// guard against a stray percent sign:
function safeDecode(s){ try { return decodeURIComponent(s); } catch { return s; } }
Python
from urllib.parse import unquote, unquote_plus, parse_qs

unquote('caf%C3%A9%20%26%20tea')      # 'café & tea'
unquote('q=caf%C3%A9+tea')            # 'q=café+tea'   + is kept
unquote_plus('q=caf%C3%A9+tea')       # 'q=café tea'
parse_qs('q=caf%C3%A9+tea')           # {'q': ['café tea']}

Rule of thumb: unquote / decodeURIComponent for a path segment; unquote_plus / URLSearchParams for a query string or form value.

FAQ

How do I decode a URL online?

Paste the encoded string into the box at the top of this page and pick the mode that matches where it came from: %20 only for a URL path, + also means space for a query string or form value. It runs in your browser — the string is never sent anywhere.

Why does %20 become a space but + stays a plus?

Because the two conventions disagree. Standard percent-decoding only understands %XX. The + → space rule comes from HTML form encoding, and only query-string parsers that copy it apply it — measured above: decodeURIComponent('a+b') returns a+b, while URLSearchParams('q=a+b').get('q') returns a b.

What is %2520?

A space that was encoded twice. The first pass made %20; the second encoded the % into %25. Decoding once gives back the text %20; decoding twice gives the space.

Is decoding the same as decrypting?

No. Percent-encoding is a reversible public format — decoding needs no key and anyone can do it. It exists so that characters survive transport, not to hide anything. Never treat an encoded string as protected data.

Does letter case matter in %3a vs %3A?

No. The hex digits are case-insensitive and both decode to :. Uppercase is the conventional output form, but either decodes correctly.
