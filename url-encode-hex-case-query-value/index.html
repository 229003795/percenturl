%2f vs %2F: same decoded byte, different URL string

The two hex digits in a percent escape are case-insensitive when you decode, but the two spellings are different characters on the wire. %2f and %2F both decode to /; a signature, cache key or dedup check that hashes the raw string will treat them as two different URLs. Decoding equivalence is not string equivalence.

Measured in two runtimes
Node.js v22.22.2 and PHP 8.5.12, same key secret-key, HMAC-SHA256 over the raw escape string. All five pairs decode to one byte, and every pair produces two different signatures.

What the URL parser actually keeps
Feed https://ex.test/p?a=%2f&b=%2F to Node's URL. The raw .search keeps both spellings exactly as written, and searchParams.get() returns / for each. But searchParams.toString() rewrites them both to uppercase %2F. A round trip through URLSearchParams can therefore change a string that a signature was computed over, even though no decoded value changed.

Encoders pick uppercase; inputs rarely do
Both standard encoders emit uppercase hex: encodeURIComponent('/') → %2F, rawurlencode('/') → %2F. The same holds for : → %3A and + → %2B. Lowercase escapes in the wild usually come from hand-built strings, a different library, or an older codebase — which is exactly why they can arrive on a signed endpoint that expected the uppercase form.
Where this actually bites
  • Signed URLs and webhooks. A request signature covers the raw bytes of the path and query. Re-encoding a value, or passing the URL through a parser that normalizes hex case, changes those bytes and fails verification.
  • Cache keys and CDNs. Two spellings are two cache entries for one resource, so a purge of %2F can miss a live %2f copy.
  • Deduplication and logs. Counting distinct raw URLs treats the pair as two, while counting decoded values treats them as one.
The fix is a policy, not a decoder: choose one canonical hex case for outgoing URLs (uppercase matches both runtimes' encoders), and normalize before signing or keying — not after.
One boundary worth knowing
Case-insensitivity only applies to the hex digits that follow %. It does not rescue a bad escape. In Node v22.22.2, decodeURIComponent('%ff') and decodeURIComponent('%FF') both throw URIError, because byte 0xFF is not valid UTF-8. Changing the case cannot turn an invalid escape into a valid one.
FAQ
Does %3a decode the same as %3A?
Yes. Both return : in Node and PHP. Letter case never changes the decoded byte.
Then why did my signed URL fail?
A signature is computed over the literal string, not the decoded value. If one side sent %2f and the other signed %2F, verification fails even though both decode to /. Check whether a parser or re-encoding step normalized the case between signing and sending.
Which case should I emit?
Uppercase. It is what encodeURIComponent and rawurlencode produce, and it is the conventional form. More important than the choice is applying one rule consistently on both sides of any signature or cache key.
