URL Encode Query Reserialization: Same Values, Different URL Bytes

URLSearchParams.sort() can change the serialized query even when every decoded key and value stays the same. For example, ?q=a%20b~ becomes ?q=a+b%7E. The spaces, tilde and decoded pair are unchanged; the URL bytes are not.

This browser-only preview does not send a request. It shows the query before and after mutating the URL object's searchParams.
What changed, and what did not
  1. Keep the original url.search string before touching searchParams.
  2. Read the decoded pairs, call url.searchParams.sort(), then read the pairs again.
  3. Compare both the pairs and the serialized query. Equal pairs do not prove equal URL bytes.
  4. If a signature, cache key or audit record uses the original spelling, treat reserialization as a meaningful mutation and test it at that boundary.

Why equal values can still break a boundary
The decoded pair ["q", "a b~"] is stable, but %20 becomes + and ~ becomes %7E. A system that signs the exact query string, compares cache keys byte-for-byte, or stores a canonical URL can therefore observe a change after a harmless-looking sort. That is an observation from this runtime, not a universal policy recommendation.
Sorting is stable for duplicate names: ?x=1&x=2 keeps both values and their order in this run. That differs from converting entries to an object, which is a separate application-level choice and is not performed by this page.
