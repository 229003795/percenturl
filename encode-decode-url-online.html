Encode Decode URL Online: Keep Values and Separators Straight

Use an online URL encoder or decoder when a link value contains spaces, symbols, or non-ASCII text—and keep the URL's own structure intact.

Quick answer: Split the URL into its parts first. Encode a value before placing it in a path segment or query parameter; leave the URL's structural separators such as ?, =, and & in place. When decoding, parse those separators before decoding the value. Open the URL Encode / Decode tool

A safe encode-and-decode sequence

  1. Identify the part that is data. For a search URL, this is often the query value after q=.
  2. Encode just that value. A component encoder turns data characters that could be misread as syntax into percent-encoded bytes.
  3. Assemble the URL. Put the encoded value after its key, retaining delimiters that separate the URL's parts.
  4. At the receiving end, parse first. Identify the parameter or path segment, then decode that one value once.

Percent encoding represents bytes inside a URL component; it is not encryption and does not make a URL private. RFC 3986 explains that reserved characters can delimit URI subparts, so changing one between a literal and a percent-encoded form can change how an application interprets the URI.

Worked example: keep an ampersand inside the search phrase

Suppose the search text is tea & cake + pie and the URL also needs a separate page parameter. Encode the search text as one component:

Raw value

tea & cake + pie

Encoded value

tea%20%26%20cake%20%2B%20pie

Assembled URL

https://example.com/search?q=tea%20%26%20cake%20%2B%20pie&page=2

The encoded %26 belongs to the phrase. The final literal & separates q from page. If the phrase's ampersand were left raw, a form-style query parser could interpret what follows it as another key/value pair.

Decode only after you know which value you are reading

When you receive the assembled link, first parse its query string into parameters. Then decode the value of q. Decoding the whole URL before parsing can turn encoded data back into characters such as & that look like delimiters, blurring the boundary between one value and the next.

Also check the format that produced the query. URLSearchParams follows application/x-www-form-urlencoded: spaces serialize as +, and a plus in parsed form data is interpreted as a space. A literal plus therefore needs the appropriate escaping (commonly %2B in that form convention). A generic component encoder may represent a space as %20. These are related conventions, not a promise that every server treats them identically.

Quick check before sharing

  • Did you encode the intended component value rather than the whole link?
  • Are the URL's ?, =, and parameter-separating & still in the right places?
  • Does the target expect form-style + or percent-encoded %20 for spaces?
  • Are you decoding only after the URL has been split into its parts?
  • Did you avoid encoding an already encoded value a second time?
